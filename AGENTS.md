# FinanceIQ — Codex Instructions

## 1. Роль и ответственность

Ты — AI software engineering agent, участвующий в разработке FinanceIQ с нуля.

Работай как опытный Fullstack-разработчик, уделяющий особое внимание:

- Корректности финансовых данных и вычислений.
- Безопасности и изоляции пользовательских данных.
- Простоте и расширяемости архитектуры.
- Поддерживаемости и тестируемости кода.
- Удобству конечного пользователя.
- Постепенной реализации функциональности согласно MVP.

Не стремись реализовать максимальное количество функций. Стремись создать надежную, понятную и качественно спроектированную систему.

## 2. Назначение продукта

FinanceIQ — персональная платформа финансовой аналитики и прогнозирования.

Приложение помогает пользователю:

1. Анализировать доходы, расходы и денежные потоки.
2. Управлять счетами и категоризировать транзакции.
3. Импортировать ручной журнал расходов и доходов из Money Manager XLSX.
4. Изучать финансовые показатели и динамику.
5. Прогнозировать доступный остаток на 30 дней.

FinanceIQ разрабатывается одновременно как практически полезное приложение и качественный портфолио-проект, демонстрирующий коммерческий подход к Fullstack-разработке.

Подробная продуктовая спецификация находится в `docs/PRODUCT.md`.

## 5. Архитектурные правила

Backend разрабатывается как модульный монолит.

Основные модули:

- Auth
- Accounts
- Transactions
- Categories
- Imports
- Analytics
- Forecasting

Придерживайся разделения ответственности:

API Router → Service → Repository → Database

Правила:

1. API Router обрабатывает HTTP-запросы и ответы.
2. Service реализует бизнес-логику.
3. Repository отвечает за взаимодействие с БД.
4. Pydantic используется для валидации входных и выходных данных.
5. SQLAlchemy используется для работы с сущностями и запросами.
6. Миграции схемы БД выполняются через Alembic.
7. Бизнес-правила не должны дублироваться между frontend и backend.

Frontend не является источником истины для финансовых расчетов.

Взаимодействие между frontend и backend осуществляется через версионированный REST API с префиксом `/api/v1`.

Предпочитай генерацию TypeScript-контрактов из OpenAPI вместо ручного дублирования API-моделей.

## 6. Финансовые инварианты

Финансовая корректность важнее удобства реализации.

Обязательные правила:

1. Денежные значения не рассчитываются с помощью binary floating-point типов.
2. Используй PostgreSQL NUMERIC и Python Decimal для денежных сумм.
3. Положительная сумма означает поступление, отрицательная — списание.
4. Переводы между собственными счетами не должны искусственно увеличивать доходы или расходы.
5. Денежный поток и остаток на счете — разные показатели.
6. Нельзя показывать расчетный текущий баланс как фактический без надежной исходной точки.
7. Все аналитические показатели должны быть воспроизводимы из исходных транзакций и подтвержденных параметров.
8. Прогноз не должен представляться как гарантированный финансовый результат.
9. При недостатке данных отображай ограничения расчета.

Детальные правила переводов, возвратов, дедупликации и прогнозирования фиксируются в `docs/PRODUCT.md`.

Не придумывай недостающие финансовые правила. Отмечай решения, требующие согласования.

## 7. Безопасность

FinanceIQ работает с чувствительной финансовой информацией.

Обязательно:

- Проверять авторизацию на сервере.
- Проверять принадлежность каждого запрашиваемого ресурса пользователю.
- Не доверять переданным клиентом идентификаторам.
- Не возвращать чужие финансовые данные.
- Использовать защищенные HttpOnly cookies согласно утвержденной схеме авторизации.
- Предусматривать защиту от CSRF для cookie-based аутентификации.
- Валидировать пользовательские данные и загружаемые файлы.
- Не записывать секреты и чувствительные финансовые данные в логи.
- Не сохранять credentials в репозитории.
- Не создавать небезопасные отладочные endpoints.

Изоляция данных пользователей должна проверяться интеграционными тестами.

## 8. Импорт Money Manager XLSX

Импорт реализуется как управляемый процесс:

Upload → Parse → Validate → Preview → Confirm

Правила:

- Для MVP согласован один профиль — `money_manager_xlsx_v1` из ручного журнала Money Manager вместо банковского CSV (2026-10-30). Полный контракт и синтетический образец находятся в `docs/IMPORT_FORMAT.md`; задача 0.7 завершена.
- Книга импортируется целиком. Перед Confirm пользователь явно сопоставляет счета Money Manager существующим собственным счетам FinanceIQ; автоматического создания счетов нет.
- Дата внесения записи не считается автоматически датой движения денег; применяются отдельно согласованные правила дат.
- Перед импортом выполняется проверка содержимого файла.
- Пользователь видит предварительный результат.
- Подтверждение должно обеспечивать согласованность записи данных.
- Повторный импорт не должен создавать непреднамеренных дубликатов.
- Неоднозначные совпадения требуют специальной обработки.
- Ошибки импорта должны быть понятны пользователю.
- Нельзя тихо отбрасывать или менять финансовые операции.

Реализация должна учитывать ограничения размера файла, количества строк и ресурсов сервера.

## 9. Правила frontend

Интерфейс должен быть:

- Понятным пользователю без финансово-технической подготовки.
- Адаптивным.
- Последовательным по стилю и поведению.
- Удобным для просмотра финансовых показателей.
- Устойчивым к пустым данным и ошибкам API.

Используй существующие компоненты и дизайн-систему.

Предусматривай:

- Loading и skeleton states.
- Empty states.
- Error states.
- Валидацию форм.
- Корректное отображение сумм и дат.
- Доступность основных действий с клавиатуры.

Не добавляй декоративные элементы в ущерб ясности финансовой информации.

4. Не добавляй зависимости без обоснования.
5. Добавляй тесты для значимой бизнес-логики.

После реализации:

## 12. Границы MVP

В MVP входят:

- Авторизация.
- Финансовые счета.
- Транзакции и категории.
- Импорт Money Manager XLSX.
- Автокатегоризация на основе правил.
- Аналитический дашборд.
- Базовый прогноз на 30 дней.

Не реализуй самостоятельно:

- Подключение банков по API.
- PDF-импорт.
- ML-категоризацию.
- Prophet или сравнение ML-моделей.
- Полноценные what-if сценарии.
- Платную подписку и биллинг.
- Микросервисную архитектуру.

Это потенциальные направления развития, а не задачи текущего MVP.
