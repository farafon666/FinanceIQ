# FinanceIQ — общие соглашения HTTP API

Контракт `/api/v1` для Auth и следующих модулей, зафиксированный в задаче 3.2. Профильный контракт каждого endpoint определяет поля запроса и ответа, применимые статусы, фильтры и правила доступа. Эти соглашения должны отражаться в схемах OpenAPI по мере подключения endpoints. [Этап 3](ROADMAP.md#этап-3-реализовать-auth-и-общий-http-контракт) · [Архитектура, §8](ARCHITECTURE.md#8-расчеты-http-и-frontend)

## 1. Ошибки и валидация

Ошибки, сформированные приложением, имеют `Content-Type: application/json` и тело с объектом `error`. Обязательные поля — стабильный машинный `code` и короткое безопасное сообщение `message`. Клиент выбирает действие и локализованный текст по `code`. При `422` объект `error` также содержит непустой массив `fields`. Для остальных статусов используются `code` и `message`.

| HTTP | `error.code` | Когда возвращается |
| --- | --- | --- |
| `400` | `invalid_json` | Тело с поддерживаемым JSON-типом содержит синтаксически некорректный JSON. |
| `401` | `invalid_credentials`, `authentication_required` | Неуспешный вход или запрос к защищённому endpoint без действующей сессии соответственно. |
| `403` | `forbidden` | Запрос отклонён проверкой доступа, `Origin` или CSRF. |
| `404` | `not_found` | Маршрут или доступный владельцу ресурс не найден. Чужой и отсутствующий ресурс дают одинаковые статус и тело. |
| `405` | `method_not_allowed` | Маршрут найден, метод не поддерживается. Ответ содержит `Allow`. |
| `409` | `conflict` | Команда конфликтует с текущим состоянием ресурса, например с занятым каноническим email при регистрации. |
| `415` | `unsupported_media_type` | Endpoint отклонил тип тела. Для регистрации и входа предусмотрен `application/json`. |
| `422` | `validation_error`, `invalid_cursor` | Запрос не проходит проверку схемы, полей или параметров. Для неприменимого курсора действует отдельный код из §2. |
| `429` | `rate_limited` | Исчерпан лимит запросов. Для Auth `Retry-After` содержит целое число секунд до конца окна. |
| `500` | `internal_error` | Непредвиденный сбой приложения, включая необработанную ошибку БД. |

Профильные ошибки могут уточнять код `4xx` в контракте endpoint. Статусы и правила Auth заданы в D-12. Неверный пароль, неизвестный email и неактивная учётная запись получают одинаковые `401 invalid_credentials` и тело ответа. Для всех ответов Auth, включая ошибки, действует `Cache-Control: no-store`. Успешный `204` имеет пустое тело и может содержать предусмотренные контрактом заголовки, в том числе `Set-Cookie`. [D-12](DECISIONS.md#d-12-auth)

Изменяющие запросы сначала проходят проверку `Origin`. При корректном `Origin` защищённый маршрут проверяет сессию и затем `X-CSRF-Token`. Отказ проверки сессии даёт `401 authentication_required`. Отказ проверки `Origin` или CSRF даёт `403 forbidden`. [D-12](DECISIONS.md#d-12-auth)

Сервер проверяет обязательность, тип и допустимые значения полей через входные схемы. Отсутствующее обязательное поле или тело даёт `422`. `null` допустим для полей, явно объявленных nullable. В JSON значения проверяются по объявленному типу. Текстовые параметры URL разбираются по формату параметра. Имена полей JSON и параметров используют `snake_case`.

Каждый элемент `fields` содержит `location` (`body`, `query`, `path` или `header`), `path` (массив имён, объявленных в схеме, и индексов массива с нуля) и `code` (`required`, `invalid_type`, `invalid_value`, `unknown_field` или `invalid_cursor`). Пустой `path` указывает на значение целиком в указанном источнике. Неизвестный ключ в объекте с фиксированным набором полей отклоняется с `unknown_field`. В `path` указывается родительский объект, включая пустой путь для корневого объекта.

Тексты ошибок формируются из безопасных шаблонов. Тела ошибок и технические логи исключают исходные значения и имена неизвестных ключей, пароли, email из Auth-запросов, cookie и их значения, CSRF-токены, хеши, финансовые реквизиты, SQL, параметры БД и stack trace. Публичный `500` общий для непредвиденных сбоев. Для диагностики в логах допустим безопасный технический код, например `database_error`.

Ответ `400` при некорректном JSON.

```json
{
  "error": {
    "code": "invalid_json",
    "message": "Проверьте формат JSON."
  }
}
```

Ответ `422` при отсутствии обязательного поля `timezone` в запросе регистрации.

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте параметры запроса.",
    "fields": [
      { "location": "body", "path": ["timezone"], "code": "required" }
    ]
  }
}
```

Для чужого и отсутствующего ресурса возвращается одинаковый `404`.

```json
{
  "error": {
    "code": "not_found",
    "message": "Ресурс не найден."
  }
}
```

Этот ответ `429` для Auth отправляется с заголовками `Retry-After: 42` и `Cache-Control: no-store`.

```json
{
  "error": {
    "code": "rate_limited",
    "message": "Слишком много запросов. Повторите позже."
  }
}
```

При сбое БД возвращается общий `500`.

```json
{
  "error": {
    "code": "internal_error",
    "message": "Не удалось обработать запрос."
  }
}
```

## 2. Курсорная пагинация

Постраничные списки принимают query-параметры `limit` (целое от 1 до 100, по умолчанию 50) и необязательный `cursor`. Запрос без `cursor` возвращает первую страницу. Ответ содержит массив `items` и `next_cursor`. Непустой `next_cursor` указывает на продолжение после последней выданной записи. Значение `null` означает конец списка и используется также для пустой страницы.

```json
{
  "items": [],
  "next_cursor": null
}
```

Клиент передаёт курсор целиком, сохраняя список, фильтры и сортировку. При их изменении клиент запрашивает первую страницу. Сервер проверяет привязку курсора к владельцу из сессии, списку, параметрам родительского ресурса, если они есть, фильтрам и сортировке. Запрос данных всегда ограничен текущим владельцем. Некорректный, пустой или неприменимый курсор возвращает одинаковый `422 invalid_cursor` с полем `{ "location": "query", "path": ["cursor"], "code": "invalid_cursor" }` без деталей о причине или владельце.

Каждый список использует устойчивый порядок с уникальным ключом в своих пределах.

| Список | Порядок |
| --- | --- |
| Операции | `occurred_on DESC, id DESC` |
| Книги импорта | `created_at DESC, id ASC` |
| Попытки внутри одной книги | `attempt_number DESC` |

Для одного неизменного набора данных последовательный обход выдаёт каждую запись один раз. Каждая страница отражает состояние списка на момент своего запроса. Если записи добавляются, удаляются или меняют соответствие фильтрам, последующие страницы отражают эти изменения в пределах продолжения. Записи, появившиеся перед позицией курсора, доступны при обновлении списка с первой страницы. [Индексы истории и операций](DATABASE_SCHEMA.md#64-реализованные-индексы-29)

## 3. Даты и технические моменты

- Календарный день передаётся строкой `YYYY-MM-DD`, например `2026-11-25`. Сервер проверяет существование даты. Значение `occurred_on` проходит между API и клиентом как календарный день без сдвига через UTC или зону профиля.
- Технический момент передаётся строкой RFC 3339. Вход должен содержать `Z` или явное смещение `±HH:MM`. Выход нормализуется в UTC с `Z`. Например, `2026-11-25T12:30:00+04:00` соответствует `2026-11-25T08:30:00Z`.
- Для отчётных периодов действует полуинтервал `[start_date, end_date)`. Если заданы обе границы, `start_date` строго меньше `end_date`. Период с `2026-11-01` по `2026-11-25` включительно передаётся с `start_date=2026-11-01` и `end_date=2026-11-26`. Календарь источника и зона прогноза определены в D-07. [D-07](DECISIONS.md#d-07-дата-операции-зона-и-календарные-границы)

## 4. Денежные значения

Во входном и выходном JSON денежная сумма имеет тип `string`, внутри backend используется `Decimal`. Входная строка содержит ASCII-цифры, необязательный начальный минус и необязательную дробную часть после точки. Должна присутствовать хотя бы одна цифра до точки и, если точка указана, хотя бы одна цифра после неё. JSON-числа, знаки `+`, экспоненты, разделители групп, запятые, пробелы, `NaN` и бесконечности отклоняются.

Входное значение должно быть точно представимо в копейках. Избыточные нули после второй дробной цифры допустимы. Хранимые суммы ограничены диапазоном `NUMERIC(18,2)`, от `-9999999999999999.99` до `9999999999999999.99`. Проверка точности и диапазона выполняется до записи. Допустимость нуля определяется бизнес-правилом поля. Для фактической операции ноль запрещён, для остатка и результата вычисления допустим. [D-01](DECISIONS.md#d-01-валюта-точность-и-округление)

Выходная строка содержит ровно две цифры после точки. Нулевой результат передаётся как `"0.00"`. Сериализация сохраняет значение, подготовленное сервером. Вычисляемые суммы округляются по `ROUND_HALF_UP` по правилам D-01, а агрегаты могут превышать диапазон одной хранимой суммы. Точное отображение на клиенте опирается на строку без преобразования в binary floating-point.

| Случай | Результат |
| --- | --- |
| `"1.230"` и `"-1.230"` на входе | Принимаются как точные `"1.23"` и `"-1.23"`. |
| `"1.231"` и `"-1.231"` на входе | `422` без округления. |
| `1.23` как JSON-число или `"1e0"` как строка | `422`. |
| `"9999999999999999.99"` как хранимая сумма | Допустимая верхняя граница. |
| `"10000000000000000.00"` | Допустимый выходной агрегат. Как входная хранимая сумма даёт `422`. |

## 5. Сценарии приёмки при подключении контракта

| Сценарий | Ожидаемый результат |
| --- | --- |
| Некорректный JSON, неподдерживаемый тип тела, отсутствующее поле и неизвестный ключ со значениями-маркерами | Соответственно `400`, `415`, `422`, `422`. Ответ при ошибке поля указывает безопасный путь. Маркеры отсутствуют в телах и технических логах. |
| Чужой и отсутствующий ID, неподдерживаемый метод, сбой БД | Одинаковые `404` для обоих ID, `405` с `Allow`, общий `500` без сведений о сбое БД. |
| Неверный пароль, неизвестный email, неактивная учётная запись при свободном лимите, исчерпанный лимит и успешный вход | Одинаковые `401` для трёх отказов, `429` с `Retry-After`, `204` с пустым телом и сессионными cookie. Во всех ответах Auth есть `Cache-Control: no-store`. |
| Операции с одинаковым `occurred_on`, пустой список, последняя страница, границы `limit` | Соседние страницы обходят все записи без пропусков и повторов на неизменном наборе. На пустой и последней странице `next_cursor: null`. Пределы `1` и `100` допустимы, `0` и `101` дают `422`. |
| Смена фильтра, повторное использование курсора другого владельца или подстановка некорректного курсора | С новым фильтром и без курсора возвращается первая страница. Старый, чужой и некорректный курсоры дают одинаковый `422 invalid_cursor`. |
| `2026-02-29`, технический момент без смещения и операции на обеих границах отчёта | Невозможная дата и момент без смещения дают `422`. Начальная граница включена, конечная исключена. |
| Денежные границы, лишние нули или ненулевая дробь сверх копеек | Проверяются примеры из §4. Максимальная хранимая сумма и более широкий агрегат сериализуются строками без потери цифр. |
| Схема OpenAPI проверяемого endpoint | Задокументированы фактические схемы ошибки и валидации, форматы дат, строковые суммы, параметры и форма страницы там, где они применяются. |

Задача 3.2 завершает спецификацию. Применение HTTP-контракта и проверки OpenAPI входят в реализацию Auth и последующих профильных endpoints.
