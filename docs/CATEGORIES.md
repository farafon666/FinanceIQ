# FinanceIQ — категории и правила категоризации

**Статус:** согласовано пользователем 2026-11-01 в задаче 0.12 / D-10. Разделы 2–7 приняты как пакет правил, раздел 8 — как 25 сценариев будущей приемки. Пункт 0.12 завершен как задача проектирования.

Документ дополняет [PRODUCT.md](PRODUCT.md), [DECISIONS.md](DECISIONS.md), [контракт импорта](IMPORT_FORMAT.md), [идентичность и повторы](IMPORT_IDENTITY.md) и [жизненный цикл фактов](FACT_LIFECYCLE.md). Физическая схема сверяется в 0.13; приложение и миграции не реализованы. Сценарии §8 описывают будущую приемку и не являются выполненными тестами.

## 1. Уже принятые основания

Повторного согласования не требуют:

- Плоские персональные категории доходов и расходов; изоляция владельцев по D-03.
- Правило «описание содержит текст» (`contains`); первое совпадение по явному приоритету.
- Сохранение ручного назначения и ручного снятия категории; изменение правил автоматически не перекатегоризирует историю.
- Категория связанного возврата наследуется от оригинала по D-05. Для несвязанного возврата нужны отдельное подтверждение смысла, ручная категоризация и предупреждение.
- Исходные категории и теги Money Manager сохраняются как реквизиты происхождения; их наличие не создает категории FinanceIQ. Описание берется из комментария, пустой комментарий остается пустым.
- Повторный импорт через `link` не переписывает категорию существующей операции по D-08. Исправление классификации сохраняет исходные реквизиты по D-13.

Разделы 2–7 — согласованный пакет уточнений этих оснований, раздел 8 — согласованные критерии будущей проверки.

## 2. Категории и их названия

У каждой категории есть собственные ID и владелец, направление `income` либо `expense`, название и признак архива. Общих изменяемых категорий с `user_id = NULL` нет. Направление после создания неизменно: для другого направления создается отдельная категория.

Входное название ограничено 100 Unicode-кодовыми точками. Для отображаемого значения применяются NFC и сворачивание пробельных последовательностей по §3 с сохранением регистра; результат должен содержать от 1 до 100 кодовых точек. Пустое название отклоняется, обрезки до лимита нет.

Для уникальности используется отдельный ключ названия `name_key`, вычисленный по `category_text_v1` (§3). В пределах одного пользователя и направления активные категории имеют разные ключи. Два пользователя могут независимо использовать одно название; одно название в `income` и `expense` также допустимо. Архивная категория не занимает активное название.

Переименование сохраняет ID и исторические назначения. История показывает текущее название категории; отдельная история прежних названий в MVP не ведется. Денежные итоги от переименования не меняются. Автоматического объединения категорий, переноса назначений и удаления категорий нет; используется архивирование по §6.

«Без категории» — вычисляемая группа для операций без назначения, а не строка справочника, начальная категория или экономический тип. Ее нельзя выбрать целью правила. Название с тем же `name_key`, что у «Без категории», зарезервировано в обоих направлениях, чтобы пользовательская категория не смешивалась с этой группой. `unclassified` остается отдельным экономическим состоянием по финансовой модели.

## 3. Сопоставление текста

Правила проверяют **только описание движения — комментарий Money Manager**. Название счета, категория и теги источника, сумма и дата не дописываются к описанию и не участвуют в `contains`. Автоматического сопоставления исходной категории с одноименной категорией FinanceIQ нет.

Одна функция `category_text_v1` применяется к описанию и шаблону, а также к ключу названия категории:

1. Применить Unicode NFC.
2. Заменить каждую последовательность Unicode-пробельных символов одним обычным пробелом U+0020, удалить пробелы по краям. Семантика — Python `str.split()` без разделителя и соединение через U+0020; в том числе обрабатываются табуляция, перенос строки и неразрывный пробел.
3. Применить Unicode `casefold()`, затем повторно NFC.

Сопоставление — буквальное вхождение получившегося шаблона в получившееся описание. Регистр не учитывается; границы слов не проверяются. Пунктуация сохраняется, `е` и `ё` различаются; транслитерации, удаления диакритики, подмены похожих латинских/кириллических букв, regex, wildcard и нечеткого поиска нет. Символы `%`, `_`, `*` и `.` в шаблоне означают сами себя.

Входной шаблон ограничен 200 Unicode-кодовыми точками. Его отображаемое значение сохраняет регистр и нормализуется как название; оно должно содержать от 1 до 200 кодовых точек. Пустой или пробельный шаблон отклоняется, чтобы не создать правило, совпадающее со всем. Расширение при `casefold`, например `ß → ss`, не обрезается. Пустое или пробельное описание не совпадает ни с одним допустимым шаблоном и остается без автоматической категории.

| Описание | Шаблон | Результат |
| --- | --- | --- |
| `ОПЛАТА   КАФЕ` | `кафе` | Совпадение |
| `Оплата` + неразрывный пробел + `кафе` | `оплата кафе` | Совпадение |
| `КАФЕ` + перенос строки + `У ДОМА` | `кафе у дома` | Совпадение |
| `Супермаркет` | `маркет` | Совпадение подстроки внутри слова |
| `Ёлка` | `елка` | Нет совпадения |
| `Cafe` | `Café` | Нет совпадения |
| `Скидка 10%` | `10%` | Буквальное совпадение |

Нормализация используется только в производном значении для сравнения. Исходный комментарий, сохраненное описание и реквизиты происхождения не меняются. Fingerprint `money_manager_match_v1` по D-08 продолжает учитывать исходный комментарий с исходными регистром, пробелами и Unicode-последовательностями; `category_text_v1` его не заменяет.

Версия алгоритма фиксируется в сервисе; версии Python и Unicode-таблиц фиксируются при подготовке окружения. Ее изменение требует отдельного решения с проверкой совместимости ключей названий и будущих назначений. Смена алгоритма не запускает перекатегоризацию истории. Версия нормализации fingerprint не используется как версия категоризации.

## 4. Приоритеты и управление правилами

Правило содержит собственные ID и владельца, целевую категорию, шаблон, `priority` и `is_active`. Направление берется из категории, отдельное изменяемое направление правила не хранится.

- `priority` — явно заданное целое число от 1 до 2 147 483 647. Меньшее число проверяется раньше; пропуски, например 10, 20, 100, допустимы.
- Приоритет уникален **среди всех активных правил пользователя**, включая оба направления. У разных пользователей приоритеты независимы. Неактивные правила могут иметь одинаковый приоритет с активными и друг с другом.
- Из подходящих по направлению активных правил побеждает первое совпавшее. Одинаковые шаблоны допустимы; выбор определяется приоритетом, а не длиной шаблона, ID или временем создания. При отсутствии совпадения категория отсутствует.
- Создание/включение активного правила с занятым приоритетом отклоняется с понятным конфликтом. Существующие правила автоматически не сдвигаются, конфликтующее правило не выключается.
- Явная перестановка нескольких приоритетов атомарна: валидируется итоговый порядок всех активных правил пользователя. Обмен 10 ↔ 20 должен быть допустим; промежуточное совпадение внутри перестановки не является конфликтом итогового порядка. Недопустимый план целиком отклоняется.
- Можно менять шаблон, приоритет и целевую собственную категорию, включать и выключать правило. Активное правило требует активной целевой категории. Выключенные правила сохраняются, удаления правил в MVP нет.
- Редактирование правила, включая смену категории или ее направления, влияет только на последующие назначения. Сохраненные категории и ссылки на правило у прежних операций не меняются.

Ссылка на правило доказывает происхождение назначения, а не соответствие его нынешним условиям. Для старой операции нельзя проверять равенство сохраненной категории нынешней цели измененного правила. Полная история редакций правил в этот MVP не входит; пользователь видит, что текущее правило могло измениться.

## 5. Начальный набор

При регистрации один раз создаются персональные копии следующего набора `default_categories_v1`:

| Направление | Названия |
| --- | --- |
| `income` | Зарплата; Подработка; Проценты |
| `expense` | Продукты; Кафе и рестораны; Транспорт; Жилье и коммунальные услуги; Здоровье; Покупки; Досуг |

У каждого пользователя свои десять категорий и ID. Начальных правил нет: система не угадывает назначение по шаблонам продавцов или исходным категориям Money Manager. Пользователь может создавать собственные категории, переименовывать и архивировать начальные на общих основаниях.

Создание набора входит в атомарное создание пользователя. Повтор запроса регистрации не добавляет копии; последующий вход, восстановление сессии и импорт не запускают создание набора. Переименованные и архивные начальные категории не восстанавливаются автоматически. Обновление состава приложения не добавляет и не меняет категории существующих пользователей без отдельного решения; постоянной связи с общим изменяемым справочником нет.

Возвраты, переводы и «Без категории» в начальный набор не входят: это соответственно экономические типы и вычисляемая группа. Отдельной автоматически подставляемой категории «Прочее» нет.

## 6. Архивирование и восстановление

Архивирование категории сохраняет ее ID, название, исторические назначения и происхождение. Операции, включая отмененные по D-13, сохраняют свои связи. Архивная категория остается видимой в истории и фильтрах; операции с ней входят в аналитику на общих основаниях. Архивирование не переводит их в «Без категории» и не меняет денежные итоги, опорные остатки или подтверждения полноты.

В одной DB-транзакции категория архивируется, все ее активные правила выключаются. Повторное архивирование уже архивной категории не создает дополнительных изменений. Новое прямое назначение архивной категории, ручное или автоматическое, запрещено. Существующее назначение можно сохранить, снять либо заменить активной категорией допустимого направления. Сохранение того же ID при редактировании другого свойства операции не считается новым назначением.

**Наследование linked refund — исключение из запрета новых прямых назначений.** Новый связанный возврат получает эффективную категорию оригинала по D-05, в том числе архивную. Это вычисляемое наследование, не ручной выбор архива. Отдельная категория у связанного возврата не назначается. Последующая смена или снятие категории оригинала отражается во всех его связанных возвратах. Для несвязанного refund новое ручное назначение допускается только в активную категорию соответствующего направления.

Восстановление возвращает ту же категорию с тем же ID в активное состояние. Если ее `name_key` уже занят активной категорией того же пользователя и направления, действие отклоняется: пользователь сначала меняет имя одной из категорий. Автоматического объединения, переименования и переноса истории нет. Архивную категорию можно переименовать; конфликт активного имени повторно проверяется при восстановлении.

Восстановление категории **не включает ее прежние правила**. Каждое правило включается явно с проверкой свободного приоритета и активной цели. Повтор восстановления уже активной категории не меняет правила. Выключенное правило можно перенаправить на другую активную собственную категорию и затем явно включить.

## 7. Назначения, preview и последствия для схемы

Автоподбор категории выполняется для новых `income`/`expense` соответствующего направления, предлагаемых через `insert` в preview. Правила не определяют экономический тип и не применяются к `transfer`, `unclassified` или `refund`. Исходный знак сам по себе не заменяет экономическую классификацию.

Ручное назначение и ручное снятие категории имеют происхождение `manual`, в том числе при `category_id = NULL`; правило их не заменяет при пересчете того же preview. Автоматическое назначение хранит фактическую категорию и ID правила; отсутствие решения — происхождение `none`. Категория linked refund вычисляется из оригинала. При `link` сохраняется существующее назначение, даже если новые правила предложили бы другое.

Изменение правил, их порядка, названия или архива категории не запускает применение правил к сохраненным операциям. Для них остается согласованное ручное исправление по D-13; массовая перекатегоризация в этот пакет не входит. Ручная смена категории пересчитывает соответствующую аналитику и прогноз по действующим правилам, но не отзывает полноту и опорные остатки.

Preview показывает фактически предлагаемую категорию и происхождение. Перед Confirm сервер повторно проверяет применимость категорий и актуальный результат правил. Изменение цели, порядка, шаблона, активности или архива, меняющее показанное назначение либо его происхождение, требует нового preview/digest. Архивирование вручную выбранной категории тоже требует нового решения: молча заменить ее другой категорией или пустым значением нельзя. Нерелевантное изменение правил, не меняющее план, само по себе не требует нового пользовательского решения. Выполненный Confirm повторно возвращает сохраненный результат по D-08, не применяя нынешние правила.

Для сверки в **0.13** по принятому пакету:

| Область | Требуемое следствие |
| --- | --- |
| `categories` | Владелец NN, неизменяемое направление, отображаемое имя, производный `name_key`, архив; частичная уникальность `(user_id, kind, name_key)` для активных. Предложение `lower(btrim(name))` из текущей схемы не эквивалентно §3 и должно быть заменено |
| `categorization_rules` | Владелец NN, FK на собственную категорию, непустой допустимый шаблон, положительный INTEGER-приоритет; частичная уникальность `(user_id, priority)` для активных; активное правило требует активной категории |
| Происхождение назначения | Различать `none/rule/manual`, включая ручное снятие; сохранять фактическую категорию и ID правила без требования соответствовать нынешней цели этого правила |
| Архив и refund | Сохранять старые назначения; запрещать новые прямые назначения в архив; разрешать вычисляемое наследование linked refund. Уточнить C-04/C-05 без запрета корректных возвратов |
| Конкуренция | Назначение и архивирование сериализуются; порядок правил читается согласованно. После ожидания блокировки выполняется повторная проверка. Атомарная перестановка не обходит итоговую уникальность |
| Регистрация | Начальные персональные категории создаются в одной транзакции с пользователем, без общих категорий и повторного добавления при входе |

Механизм поддержания `name_key`, ограничения прямой записи, блокировки, физические поля provenance и перестановка приоритетов должны быть сверены в 0.13 с проверками сервис/БД/тест. Этот документ не утверждает готовую схему, новые endpoints или переход к реализации.

## 8. Сценарии будущей приемки

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| CAT-01 | Два подходящих правила с приоритетами 10 и 20; второе имеет более длинный шаблон | Побеждает 10, длина не влияет; направление берется из категории |
| CAT-02 | Первое правило выключено либо относится к другому направлению | Проверяется следующее подходящее активное правило |
| CAT-03 | Два активных правила одного пользователя получают один приоритет, в том числе разных направлений | Создание/включение/изменение отклоняется; другой пользователь и неактивное правило независимы |
| CAT-04 | Приоритет 0, отрицательный, дробный или выше INTEGER; обмен 10 ↔ 20 | Неверные значения отклоняются; допустимый обмен атомарен, ошибка итогового плана ничего не меняет |
| CAT-05 | Варианты регистра, обычных/неразрывных пробелов, табуляции и переносов строки | Одинаковый результат `contains`; исходные значения не меняются |
| CAT-06 | NFC-составной/разложенный текст; `Straße` и `STRASSE`; `е/ё`, `Cafe/Café`, похожие латинские/кириллические буквы | Канонически равные формы и casefold совпадают; остальные различия сохраняются |
| CAT-07 | Шаблоны `%`, `_`, `*`, `.`; подстрока внутри слова | Символы буквальные; границы слов не требуются |
| CAT-08 | Пустой/пробельный шаблон; длина 200/201; пустое/пробельное описание; нет совпадения | Недопустимый шаблон отклоняется без обрезки; допустимое описание без совпадения не получает категорию |
| CAT-09 | Слова есть только в категории/тегах/имени счета Money Manager | Правило по описанию не совпадает; исходные реквизиты сохраняются |
| CAT-10 | Нормализация описания для правил; исходные комментарии различаются регистром или пробелами | Совпадение категорий возможно, но сохраненный комментарий и fingerprint D-08 не переписываются |
| CAT-11 | Имена равны после §3; другой пользователь/направление; пустое, зарезервированное или слишком длинное имя | Дубликат активного ключа в своей области и недопустимые имена отвергаются; независимые области разрешены |
| CAT-12 | Первая регистрация, повтор запроса, вход, обновление приложения после переименования/архива начальной категории | Создаются ровно десять своих категорий один раз, правил нет; последующие действия набор не восстанавливают |
| CAT-13 | Ручное назначение/снятие в preview; повторный расчет правил и повторный импорт через `link` | Ручное решение сохраняется; `manual` с NULL отличается от `none`; существующий факт не меняется |
| CAT-14 | Правило меняет шаблон, порядок, активность, категорию или ее направление после назначения | Старая операция сохраняет фактическую категорию и ссылку на правило; автоматического применения к истории нет |
| CAT-15 | Переименование категории; попытка сменить ее направление | ID и назначения сохраняются, история показывает новое имя, суммы прежние; смена направления отклоняется |
| CAT-16 | Архивирование категории с историческими назначениями и несколькими правилами, затем повтор действия | Архив и выключение правил атомарны; история/фильтры/итоги сохранены; повтор не меняет состояние |
| CAT-17 | Новое ручное/автоматическое назначение в архив; снятие старого назначения; включение правила на архив | Новое назначение и включение запрещены; сохранение/снятие/замена старого назначения допустимы по §6 |
| CAT-18 | Новый linked refund к оригиналу с архивной категорией; смена/снятие категории оригинала | Возврат наследует эффективную категорию, включая архивную; последующее изменение отражается в нем без отдельного назначения |
| CAT-19 | Несвязанный refund обоих знаков; попытка применить правило к refund/transfer/unclassified | Только допустимая ручная категория несвязанного refund после подтверждения D-05; правила экономический тип не меняют |
| CAT-20 | Архив освободил имя, создана новая одноименная категория; восстановление старой, затем переименование | Восстановление с конфликтом отклоняется; после устранения конфликта возвращается старый ID, история не объединяется |
| CAT-21 | Восстановление категории и повтор действия; включение ее прежнего правила с занятым приоритетом | Правила остаются выключенными; включение с конфликтом отклоняется без скрытого сдвига |
| CAT-22 | Между preview и Confirm изменилось правило/архив; уже выполненный Confirm повторен после изменений | Изменившийся план требует нового preview; выполненный Confirm возвращает прежний результат без перекатегоризации |
| CAT-23 | Одновременное назначение/архивирование; одновременные перестановки/включения правил | Не возникает нового прямого назначения в архив и двух активных одинаковых приоритетов; нет частично примененного порядка |
| CAT-24 | Чужие ID категории/правила через API и прямую запись в PostgreSQL, чужой список/изменение | Чтение и изменение изолированы; составные FK отклоняют чужую связь, чужие данные не раскрываются |
| CAT-25 | Изменение категории, архивирование и восстановление при подтвержденных остатках/полноте; операции отмененной книги | Денежные движения, опоры и полнота прежние; история отмены и назначений сохранена, отмененные факты не возвращаются в расчеты |

Проверки CAT-01–CAT-25 должны быть реализованы вместе с соответствующими модулями, включая интеграционные проверки на PostgreSQL для ограничений, конкуренции и изоляции.
